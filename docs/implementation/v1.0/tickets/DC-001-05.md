# DC-001-05 — Account lifecycle pages

/forgot-password, /reset-password, and /claim pages rendering <ForgotPassword>, <ResetPassword>, and <ClaimAccount> from @poly-x/next. Tokens read from searchParams in Server Components and passed as props to avoid hydration mismatch.

**Contract:** /forgot-password -> <ForgotPassword signInPath='/sign-in' />; /reset-password -> <ResetPassword token={token} signInPath='/sign-in' forgotPasswordPath='/forgot-password' />; /claim -> <ClaimAccount token={token} signInPath='/sign-in' />; token from searchParams in RSC

## Why

REQ-FUNC-001 requires that administrators can recover passwords and claim provisioned accounts. The account lifecycle pages render Poly-X components for these flows so that password reset and account claiming are provided by Poly-X, not built locally.

## What

The /forgot-password, /reset-password, and /claim pages render <ForgotPassword>, <ResetPassword>, and <ClaimAccount> from @poly-x/next respectively, with tokens read from searchParams in Server Components and passed as props to avoid hydration mismatch.

## Scope

**In:** The three account lifecycle page components (/forgot-password, /reset-password, /claim), token reading from searchParams in Server Components, and the component prop configuration.

**Out:** BFF catch-all route (DC-001-01), edge gate middleware (DC-001-02), token introspection and admin role enforcement (DC-001-03), sign-in page UI (DC-001-04), and notification dispatch (separate component via Poly-X poly-alert). Poly-X provides the password reset and account claiming flows; no custom reset form or claiming logic is built here.

## Tasks

- [ ] **T1** — Create the /forgot-password page rendering <ForgotPassword signInPath="/sign-in" /> from @poly-x/next _(verify: navigating to /forgot-password renders the Poly-X ForgotPassword component with a link back to /sign-in; the platform sends the reset email and answers identically whether or not the address exists)_
- [ ] **T2** — Create the /reset-password page as a Server Component that reads the token from searchParams and passes it as a prop to <ResetPassword token={token} signInPath="/sign-in" forgotPasswordPath="/forgot-password" /> _(verify: navigating to /reset-password?token=valid renders the Poly-X ResetPassword component with the token; navigating to /reset-password without a token reports an invalid link; no hydration mismatch occurs on first render because the token is read server-side from searchParams)_
- [ ] **T3** — Create the /claim page as a Server Component that reads the token from searchParams and passes it as a prop to <ClaimAccount token={token} signInPath="/sign-in" /> from @poly-x/next _(verify: navigating to /claim?token=valid renders the Poly-X ClaimAccount component; the route is public and reachable while signed in so an authenticated user can still claim the account their link was sent for; no hydration mismatch occurs because the token is read server-side)_
- [ ] **T4** — Verify that /claim is not placed in a signed-out-only set that bounces authenticated users away, and that the route remains reachable while signed in _(verify: an authenticated GET to /claim?token=valid returns 200 and renders the ClaimAccount component without redirecting to sign-in)_
- [ ] **T5** — Verify the three pages have no hard-coded user-facing text (all strings come from Poly-X or a locale file) and meet WCAG 2.2 AA: form inputs have labels, keyboard reach works, focus is visible, and colour contrast meets the AA threshold _(verify: no user-facing string is hard-coded in any of the three page components; all text is provided by the Poly-X components or a locale file; forms are fully navigable by keyboard with visible focus indicators and labels on all inputs)_
- [ ] **T6** — Definition of Done: the /forgot-password, /reset-password, and /claim pages render their respective Poly-X components with tokens read from searchParams in Server Components, /claim is reachable while signed in, no hydration mismatch occurs, i18n and accessibility (WCAG 2.2 AA) are verified, the build passes, and the pages are deployed to the test environment _(verify: all three pages render their Poly-X components with correct props; tokens are read from searchParams server-side with no hydration mismatch; /claim is reachable while signed in; no hard-coded user-facing text; keyboard navigation and focus indicators meet WCAG 2.2 AA; a build passes; the pages are deployed to the test environment)_

## Acceptance

- Given an unauthenticated request to any admin dashboard route, When the system checks the Poly-X session, Then the system returns HTTP 401 and does not display the dashboard
- Given an authenticated request whose Poly-X token lacks the admin role, When the system checks the role grant, Then the system returns HTTP 403 and does not display the dashboard
- Given an authenticated request with the admin role, When the system checks the Poly-X session, Then the system grants access to the admin dashboard
