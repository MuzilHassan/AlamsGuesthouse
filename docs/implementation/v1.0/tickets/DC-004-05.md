# DC-004-05 — Room listings management UI

Admin dashboard pages for room listings list, create-room form, and edit-room form. Forms include image upload fields that call /api/admin/upload. Accessible at /admin/rooms. Conforms to WCAG 2.2 AA.

**Contract:** Pages at /admin/rooms, /admin/rooms/new, /admin/rooms/:id/edit; forms with name, description, amenities, images, maxOccupancy, price fields; image upload calls /api/admin/upload; zod validation; WCAG 2.2 AA

## Why

REQ-FUNC-004, REQ-FUNC-005, REQ-FUNC-006, and REQ-FUNC-011 require an admin dashboard UI for creating, editing, deleting room listings, and updating room prices, with the results reflected in the room listings list and on the public site.

## What

Admin dashboard pages at /admin/rooms (list), /admin/rooms/new (create form), and /admin/rooms/:id/edit (edit form) with fields for name, description, amenities, images, maxOccupancy, and price, image upload calling /api/admin/upload, zod validation on the client, and WCAG 2.2 AA compliance.

## Scope

**In:** The three admin dashboard pages (/admin/rooms, /admin/rooms/new, /admin/rooms/:id/edit), their form components with all room fields, the image upload integration with /api/admin/upload from DC-003-01, client-side zod validation, the delete confirmation dialog, and accessibility compliance to WCAG 2.2 AA.

**Out:** Does not build the POST /api/admin/rooms endpoint (DC-004-01), the PUT /api/admin/rooms/:id endpoint (DC-004-02), the DELETE endpoint (DC-004-03), the price-only endpoint (DC-004-04), or the image upload endpoint itself (DC-003-01). Poly-X provides authentication; these pages consume the SDK session context and the API endpoints from DC-004-01 through DC-004-04.

## Tasks

- [ ] **T1** — Build the room listings list page at /admin/rooms: fetch rooms from the API, display each room's name, price, maxOccupancy, and a thumbnail of the first image, with edit and delete action buttons per row, and a 'New Room' button linking to /admin/rooms/new _(verify: an authenticated admin visiting /admin/rooms sees the list of rooms with name, price, maxOccupancy, first image thumbnail, edit button, and delete button for each row, and a 'New Room' button)_
- [ ] **T2** — Build the create-room form page at /admin/rooms/new with fields for name (text input with label), description (textarea with label), amenities (multi-input with label), images (file upload calling /api/admin/upload from DC-003-01), maxOccupancy (number input with label), and price (amount and currency inputs with labels); apply client-side zod validation matching the server schema (name non-blank, price positive, maxOccupancy positive) _(verify: the form renders all fields with associated labels; submitting with a blank name shows a validation error naming the name field without calling the API; submitting valid data calls POST /api/admin/rooms and on 201 redirects to /admin/rooms with the new room visible in the list)_
- [ ] **T3** — Build the edit-room form page at /admin/rooms/:id/edit: pre-populate all fields from the existing room data fetched via the API, allow editing any field, wire the image upload to /api/admin/upload for adding or replacing images, submit via PUT /api/admin/rooms/:id, and add a delete confirmation dialog that calls DELETE /api/admin/rooms/:id and redirects to /admin/rooms on 204 _(verify: visiting /admin/rooms/:id/edit shows the form pre-populated with the room's current values; changing price to 4500 and saving calls PUT and on 200 redirects to /admin/rooms with the updated price visible; removing all amenities and saving stores an empty amenities list; confirming deletion calls DELETE and on 204 redirects to /admin/rooms with the room absent from the list)_
- [ ] **T4** — Add the price-only update control on the edit form: a dedicated price field that can be saved independently via PUT /api/admin/rooms/:id/price, with validation that rejects non-positive values on the client before submission _(verify: changing the price to 3500 and using the dedicated price save calls PUT /api/admin/rooms/:id/price and on 200 shows the updated price in the form and list; entering 0.00 shows a client-side validation error naming the price field without calling the API)_
- [ ] **T5** — Ensure WCAG 2.2 AA compliance across all three pages: verify all form inputs have associated label elements, keyboard reach and focus management work for all interactive elements (tab order, focus on error, focus trap in the delete confirmation dialog), color contrast meets AA ratios for text and controls, no hard-coded user-facing text (all labels, button text, error messages, and headings use locale-aware string resources) _(verify: an axe-core or Lighthouse accessibility audit on /admin/rooms, /admin/rooms/new, and /admin/rooms/:id/edit reports no violations at WCAG 2.2 AA; all interactive elements are reachable by keyboard; the delete confirmation dialog traps focus and returns focus on close; all user-facing strings are sourced from locale resource files, not inline literals)_
- [ ] **T6** — Write integration tests covering the UI flows for TC-010 (create room via form, appears in list), TC-011 (blank name shows validation error), TC-012 (edit price to 4500, updated price in list), TC-013 (remove amenities, empty list stored), TC-014 (delete confirmation removes room from list), TC-020 (price update to 3500 via dedicated control, public site shows 3500), and TC-021 (non-positive price shows validation error) _(verify: all seven UI flow tests pass: creating a room via the form shows it in the list, blank name shows a field-level error, editing price to 4500 updates the list, removing amenities stores an empty list, delete confirmation removes the room, price update to 3500 reflects on the public site, and entering 0.00 as price shows a validation error naming the price field)_
- [ ] **T7** — Definition of Done: all UI tests pass, the three pages render and function correctly for create, edit, delete, and price update flows, client-side validation matches the server schema, image upload calls /api/admin/upload, the pages meet WCAG 2.2 AA with no axe-core violations, all user-facing text is locale-aware, and the pages are deployed to the test environment _(verify: the test suite passes all seven UI flow tests, an accessibility audit reports zero WCAG 2.2 AA violations, navigating to /admin/rooms on the test environment shows the room list, and the create and edit forms submit successfully to the respective API endpoints)_

## Acceptance

- Given an authenticated admin on the room listings section, When the admin submits a create-room form with name, description, amenities, images, maximum occupancy, and price, Then the system stores the room listing in the data store and displays it in the room listings list
- Given an authenticated admin submits a create-room form with a blank name, When the system validates the submission, Then the system rejects the submission with a validation error message naming the name field
- Given an authenticated admin and an existing room listing, When the admin changes the price field to 4500 and saves, Then the system updates the stored room listing with the new price and the updated price appears in the room listings list
- Given an authenticated admin and an existing room listing, When the admin removes all amenities and saves, Then the system stores the room listing with an empty amenities list
- Given an authenticated admin and an existing room listing, When the admin confirms deletion of that listing, Then the system removes the room listing from the data store and the listing no longer appears in the room listings list or on the public site
- Given an authenticated admin and an existing room listing priced at 3000, When the admin changes the price to 3500 and saves, Then the system stores the updated price and the public site displays 3500 for that room on the next page load
