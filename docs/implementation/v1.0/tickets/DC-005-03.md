# DC-005-03 — PUT /api/admin/hero-images/reorder

Reorder hero images by accepting an array of image IDs in the new order and updating display_position for each.

**Contract:** PUT /api/admin/hero-images/reorder { orderedIds: string[] } -> 200 { heroImages[] } | 401 | 403 | 422 | 503

## Why

REQ-FUNC-009 requires that an authenticated admin can reorder hero carousel images so the public site displays them in the new order on the next page load.

## What

PUT /api/admin/hero-images/reorder accepts an orderedIds array, updates displayPosition for each image in PostgreSQL, and returns 200 with the heroImages array in the new order; it returns 422 for invalid input, 401 for an unauthenticated caller, 403 for a non-admin, and 503 when Poly-X is unreachable.

## Scope

**In:** The PUT /api/admin/hero-images/reorder endpoint, batch displayPosition update logic, input validation of orderedIds, Poly-X introspection middleware wiring, structured logging, and integration tests.

**Out:** The POST endpoint (DC-005-01), the DELETE endpoint (DC-005-02), the admin management UI (DC-005-04), the image upload endpoint (DC-003-01), and the public hero-images read endpoint. Authentication is provided by Poly-X via DC-001-03; this unit wires it, it does not build login or token handling. The hero_images table migration is owned by DC-005-01.

- [ ] **T3** — Add structured logging with the request id on each reorder call, logging the number of images reordered and the admin userId, without logging the token _(verify: a successful reorder logs the request id, userId, count of reordered images, and outcome 'reordered'; a 422 rejection logs the request id and outcome 'rejected' with the validation reason; no token value appears in any log line)_
