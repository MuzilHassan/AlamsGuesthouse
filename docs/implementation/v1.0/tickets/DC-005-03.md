# DC-005-03 — PUT /api/admin/hero-images/reorder

Reorder hero images by accepting an array of image IDs in the new order and updating display_position for each.

**Contract:** PUT /api/admin/hero-images/reorder { orderedIds: string[] } -> 200 { heroImages[] } | 401 | 403 | 422 | 503

## Why

REQ-FUNC-009 requires that an admin can reorder hero carousel images, so that the public site displays the carousel images in the new order on the next page load.

## What

PUT /api/admin/hero-images/reorder accepts an array of image IDs in the new order, updates displayPosition for each in a Prisma transaction, and returns 200 with the reordered heroImages array.

## Scope

**In:** The PUT /api/admin/hero-images/reorder endpoint, its transactional reorder logic via Prisma, and the Poly-X introspection middleware wiring for admin authorization.

**Out:** The POST and DELETE endpoints (DC-005-01, DC-005-02), the admin UI page (DC-005-04), and the public-site hero carousel rendering. Poly-X provides authentication and authorization via the introspection middleware from DC-001-03; this unit does not build login, token signing, or password handling.

## Tasks

- [ ] **T1** — Implement the PUT /api/admin/hero-images/reorder route handler that validates orderedIds is a non-empty array of string IDs, then in a single Prisma transaction updates displayPosition for each hero image to its index in the array, and returns 200 with the heroImages array in the new order _(verify: PUT /api/admin/hero-images/reorder with orderedIds placing the image formerly in position 3 first returns 200 with the heroImages array in the new order; an empty orderedIds array returns 422; a non-array orderedIds returns 422; an orderedIds containing a non-existent id returns 422)_
- [ ] **T2** — Wire the Poly-X introspection middleware from DC-001-03 before the handler: call polyx.auth.introspect on the bearer token, check the admin role in permissions.modulePermissions, validate the organization-id header against the token organization, and fail closed with 401 for an inactive token, 403 for a missing admin role or org-id mismatch, and 503 when Poly-X is unreachable within the 5s timeout _(verify: a PUT request with an expired or revoked token returns 401; a valid token without admin role returns 403; a mismatched organization-id header returns 403; Poly-X unreachable returns 503; a valid admin token with matching organization-id proceeds to the handler)_
- [ ] **T3** — Add unit and integration tests covering TC-017: the 200 success path reordering images by moving position 3 to position 1 and confirming the new order via GET /api/content/hero-images, the 422 validation path for invalid orderedIds, the 401 unauthenticated path, the 403 missing admin role path, and the 503 Poly-X unreachable path _(verify: the test suite passes: TC-017 returns 200 with heroImages in the new order after moving position 3 to position 1; GET /api/content/hero-images reflects the new order; 422 for empty or invalid orderedIds; 401 for no token; 403 for non-admin role; 503 for Poly-X unreachable)_
- [ ] **T4** — Add structured logging with the request id on every PUT /api/admin/hero-images/reorder call, and a counter metric for hero image reorders _(verify: a successful PUT logs a structured entry with the request id, the number of reordered images, and the action 'hero_image_reorder'; the counter metric increments by 1 per reorder operation)_
- [ ] **T5** — Definition of Done: verify the endpoint is deployed to the test environment, all tests pass, the Poly-X middleware is wired, structured logging and metrics are present, and the API documentation describes the PUT /api/admin/hero-images/reorder operation with its 200, 401, 403, 422, and 503 responses _(verify: in the test environment, PUT /api/admin/hero-images/reorder with a valid orderedIds array returns 200 with the reordered heroImages for a valid admin request; all unit and integration tests pass; the API docs list the endpoint with its response codes and the polyxBearer security scheme)_

## Acceptance
