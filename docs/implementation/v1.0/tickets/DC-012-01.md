# DC-012-01 — Notification dispatcher unit

Module that calls poly-alert for email and in-app notifications. Uses @poly-x/sdk to call POST /v1/email/send and POST /v1/push. Retries on transient failures with exponential backoff and jitter (max 3 retries, base 1s). Records delivery status. Routes to dead-letter path after max retries. 10-second timeout per call. Does not block content operations.

**Contract:** dispatchNotification({ type, recipient, channel, content }) -> calls poly-alert POST /v1/email/send or POST /v1/push; 10s timeout; retry x3 with backoff+jitter; dead-letter on max retries; delivery status recorded; non-blocking

## Why

Content events need to notify recipients through email and in-app channels so that users are informed of relevant activity without the product building its own mailer or notification store, satisfying REQ-FUNC-001 by delegating delivery to the Poly-X poly-alert service.

## What

A notification dispatcher module that calls poly-alert POST /v1/email/send and POST /v1/push via @poly-x/sdk, with a 10-second timeout per call, retry up to 3 times with exponential backoff and jitter, delivery status recorded for each attempt, dead-letter routing after max retries, and non-blocking dispatch from content operations.

## Scope

**In:** The dispatchNotification function and its retry, timeout, delivery-status recording, and dead-letter routing logic; wiring content event triggers to the dispatcher in a non-blocking manner; configuration of POLYX_SECRET_KEY and POLY_ALERT_BASE_URL for the poly-alert calls.

**Out:** Does not build authentication, token verification, or role checks: those come from DC-001-03 (Poly-X introspection middleware). Does not send email, SMS, or push directly: Poly-X poly-alert delivers them. Does not define which specific content events trigger notifications: that is an open question for the client. Does not build a notification store or template management: Poly-X owns those.

## Acceptance

- Given an unauthenticated request to any admin dashboard route, When the system checks the Poly-X session, Then the system returns HTTP 401 and does not display the dashboard
- Given an authenticated request whose Poly-X token lacks the admin role, When the system checks the role grant, Then the system returns HTTP 403 and does not display the dashboard
- Given an authenticated request with the admin role, When the system checks the Poly-X session, Then the system grants access to the admin dashboard
