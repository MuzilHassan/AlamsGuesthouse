# DC-012-01 — Notification dispatcher unit

Module that calls poly-alert for email and in-app notifications. Uses @poly-x/sdk to call POST /v1/email/send and POST /v1/push. Retries on transient failures with exponential backoff and jitter (max 3 retries, base 1s). Records delivery status. Routes to dead-letter path after max retries. 10-second timeout per call. Does not block content operations.

**Contract:** dispatchNotification({ type, recipient, channel, content }) -> calls poly-alert POST /v1/email/send or POST /v1/push; 10s timeout; retry x3 with backoff+jitter; dead-letter on max retries; delivery status recorded; non-blocking

## Why

Users must be notified when content events occur (REQ-FUNC-001), so that recipients receive timely email or in-app notifications through Poly-X poly-alert without the product building or operating its own mailer.

## What

The notification dispatcher calls poly-alert POST /v1/email/send and POST /v1/push on content event triggers, retries transient failures up to 3 times with exponential backoff and jitter, routes unrecoverable sends to a dead-letter path, records delivery status for each attempt, and does not block content operations.

## Scope

**In:** The notification dispatcher module with dispatchNotification({ type, recipient, channel, content }) that calls Poly-X poly-alert for email and in-app push, with retry logic (exponential backoff with jitter, max 3 retries, base 1s), 10-second timeout per call, delivery status recording, dead-letter path after max retries, non-blocking dispatch, and wiring of the Poly-X introspection middleware from DC-001-03 on admin dashboard routes

**Out:** Does not build authentication, token introspection, or session management (provided by DC-001-03 via @poly-x/sdk); does not define which content events trigger notifications (open question for the client); does not send email, SMS, or push directly (Poly-X poly-alert delivers them); does not build email templates or notification content formatting; does not build the admin dashboard UI

## Acceptance

- Given an unauthenticated request to any admin dashboard route, When the system checks the Poly-X session, Then the system returns HTTP 401 and does not display the dashboard
- Given an authenticated request whose Poly-X token lacks the admin role, When the system checks the role grant, Then the system returns HTTP 403 and does not display the dashboard
- Given an authenticated request with the admin role, When the system checks the Poly-X session, Then the system grants access to the admin dashboard
