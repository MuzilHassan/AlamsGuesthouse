# DC-002-06 — BlogPost table

Prisma schema for BlogPost table storing blog posts with title, body, image URL, and published status.

**Contract:** BlogPost { id UUID PK, title text not null, body text not null, image_url text nullable, is_published boolean not null default false, created_at timestamp not null, updated_at timestamp not null }

## Why

REQ-FUNC-020 and REQ-NFUNC-006 require blog posts to persist across restarts and deployments so published and draft content remains available without data loss.

## What

A BlogPost table in PostgreSQL 16 defined via a Prisma 6 schema with migration and rollback, storing blog post title, body, optional image URL, and published status.

## Scope

**In:** The Prisma model and migration for the BlogPost table only: columns id (UUID PK), title (text not null), body (text not null), image_url (text nullable), is_published (boolean not null default false), created_at, updated_at.

**Out:** The Prisma client configuration (DC-002-07); any blog post rendering, SEO, or content formatting logic; API endpoints that serve blog posts.

## Tasks

- [ ] **T1** — Add the BlogPost model to prisma/schema.prisma with id as @id @db.Uuid, title as String not null, body as String not null, image_url as String?, is_published as Boolean not null with @default(false), created_at and updated_at as DateTime not null _(verify: prisma validate succeeds and the BlogPost model matches the contract fields, types, and the default false on is_published)_
- [ ] **T2** — Generate the Prisma migration for the BlogPost table (prisma migrate dev --name add_blog_post_table) and verify the up SQL creates the blog_post table with all contract columns and is_published defaulting to false _(verify: the migration SQL creates blog_post with id uuid PK default gen_random_uuid(), title text not null, body text not null, image_url text, is_published boolean not null default false, created_at timestamp not null, updated_at timestamp not null)_
- [ ] **T3** — Write the down migration that drops the blog_post table, so the migration is reversible _(verify: running the down migration removes the blog_post table cleanly)_
- [ ] **T4** — Write a unit test that inserts a BlogPost without specifying is_published, simulates a restart by re-instantiating the PrismaClient, and reads the record back to confirm is_published defaults to false and all fields are unchanged; also test inserting with image_url null _(verify: the test creates a blog_post with title and body, re-instantiates the client, reads the record and confirms is_published=false and image_url is null; a second insert with image_url set reads back the same value; TC-031 is demonstrated)_
- [ ] **T5** — Definition of Done: run prisma validate, apply the migration and its rollback, and run the persistence test suite for BlogPost _(verify: prisma validate passes, the blog_post migration applies and rolls back without error, the persistence test passes confirming blog post content survives a simulated restart, and the schema is committed)_

## Acceptance

- Given managed content stored in the data store, When the application is restarted or redeployed, Then the managed content remains available in the data store unchanged
- Given managed content in the data store, When the application undergoes a restart or deployment, Then an inspection of the data store shows all managed content present and unchanged
