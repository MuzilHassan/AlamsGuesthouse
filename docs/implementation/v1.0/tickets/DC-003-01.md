# DC-003-01 — POST /api/admin/upload

Admin endpoint that accepts a multipart image file, sends it to Cloudinary via the cloudinary SDK, and returns the Cloudinary URL. Requires Poly-X admin auth. 10-second timeout on Cloudinary call. Returns 422 on upload failure with error message.

**Contract:** POST /api/admin/upload (multipart file) -> 200 { url: cloudinaryUrl } | 401 | 403 | 422 upload failed | 503 Poly-X unreachable; 10s timeout on Cloudinary call; no partial reference stored on failure

## Why

REQ-FUNC-010 requires all dashboard images to be uploaded to Cloudinary with the returned URL stored as the image reference, so that admins can manage imagery through the dashboard and the system holds a durable Cloudinary URL rather than a local file path.

## What

A POST /api/admin/upload endpoint that accepts a multipart image file, authenticates the caller through Poly-X introspection with an admin role check, uploads the file to Cloudinary within a 10-second timeout, and returns 200 with the Cloudinary URL, or 422 on upload failure with no partial reference stored.

## Scope

**In:** The POST /api/admin/upload route, multipart file parsing, Cloudinary SDK integration with a 10s timeout, Poly-X introspection and admin-role authorization wiring (consuming the DC-001-03 middleware contract), error responses (401, 403, 422, 503), structured request logging, and automated tests for TC-018 and TC-019 plus the auth error paths.

**Out:** Persisting the returned Cloudinary URL into the data store (done by the calling dashboard component or a separate persistence step), the admin dashboard UI that triggers the upload, the Poly-X introspection middleware implementation itself (provided by DC-001-03), Cloudinary account provisioning and upload preset configuration, and any image transformation or resizing logic.

## Tasks

- [ ] **T1** — Install the Cloudinary SDK and add the required environment variables (CLOUDINARY_CLOUD_NAME, CLOUDINARY_API_KEY, CLOUDINARY_API_SECRET) to the environment configuration, naming them per environment without values _(verify: the Cloudinary SDK package is installed and the three environment variable names are present in the configuration template with no hardcoded values; a missing variable causes a startup error naming the missing key)_
- [ ] **T2** — Scaffold the POST /api/admin/upload route with multipart file parsing that accepts a single image file field and validates the content type is an image (JPEG, PNG, WebP, GIF) _(verify: a POST to /api/admin/upload with no file returns 422 with a message naming the missing file field; a POST with a non-image content type returns 422 with a message naming the invalid content type)_
- [ ] **T3** — Wire the Poly-X introspection middleware from DC-001-03 in front of the upload route: call polyx.auth.introspect on the bearer token, check that the caller has the admin role in permissions.modulePermissions, validate the organization-id header against the token's organizationId, and fail closed with 401 on an inactive token, 403 on a missing admin role or organization-id mismatch, and 503 when Poly-X is unreachable within the 5s timeout _(verify: a request with no bearer token returns 401; a request with a valid token but no admin role returns 403; a request with a valid admin token but a mismatched organization-id header returns 403; a request when Poly-X is unreachable returns 503; no request reaches the Cloudinary upload code without passing all three checks)_
- [ ] **T4** — Implement the Cloudinary upload call using the Cloudinary SDK with a 10-second timeout, and on success return 200 with { url: cloudinaryUrl } where cloudinaryUrl is the secure_url from the Cloudinary response _(verify: a POST to /api/admin/upload with a valid admin token and a 500KB JPEG returns 200 with a body containing { url } where url is a Cloudinary secure URL; the upload completes within the 10s timeout or is aborted)_
- [ ] **T5** — Handle Cloudinary upload failures: catch errors and timeouts from the Cloudinary SDK call and return 422 with an error message indicating the upload failed, ensuring no partial image reference is written to the data store or response before the Cloudinary call succeeds _(verify: when the Cloudinary SDK throws an error or the 10s timeout fires, the endpoint returns 422 with a JSON body containing an error message stating the upload failed; no partial image reference exists in the data store or in any intermediate state after the failure)_
- [ ] **T6** — Add structured logging with the request id, the authenticated userId, the file size and content type, the Cloudinary upload duration, and the outcome (success or failure with the error code), emitted on every request _(verify: a successful upload logs the request id, userId, file size, content type, upload duration in ms, and outcome 'success' with the Cloudinary URL; a failed upload logs the same fields with outcome 'failure' and the Cloudinary error code; no token or secret appears in the log output)_
- [ ] **T7** — Write automated tests covering TC-018 (valid admin upload of a 500KB JPEG returns 200 with a Cloudinary URL), TC-019 (Cloudinary failure returns 422 with no partial reference stored), and the auth error paths (401 unauthenticated, 403 non-admin or org-id mismatch, 503 Poly-X unreachable), using a Cloudinary test stub and a Poly-X sandbox token _(verify: the test suite runs TC-018 and asserts a 200 response with { url } matching a Cloudinary URL pattern; TC-019 asserts a 422 response and verifies the data store contains no partial reference; the auth tests assert 401, 403 (role), 403 (org-id), and 503 respectively; all tests pass)_
- [ ] **T8** — Definition of Done: verify the endpoint is deployed to the test environment, all tests pass, the Cloudinary and Poly-X environment variables are documented in the runbook, the API description for POST /api/admin/upload is recorded with its request, response, and error codes, and both acceptance criteria are demonstrated end to end _(verify: the test environment deployment responds to POST /api/admin/upload; the full test suite passes including TC-018 and TC-019; the runbook lists CLOUDINARY_CLOUD_NAME, CLOUDINARY_API_KEY, CLOUDINARY_API_SECRET, and POLYX_SECRET_KEY with their purpose; the API documentation describes the multipart request, the 200 { url } response, and the 401, 403, 422, and 503 error responses; an authenticated admin upload succeeds and returns a Cloudinary URL, and a Cloudinary failure returns 422 with no partial reference stored)_

## Acceptance

- Given an authenticated admin submitting an image through the dashboard, When the image is uploaded, Then the system sends the image to Cloudinary and stores the returned Cloudinary URL as the image reference in the data store
- Given an authenticated admin submitting an image and the Cloudinary upload fails, When the system receives an error response from Cloudinary, Then the system rejects the submission with an error message indicating the upload failed and does not store a partial image reference
